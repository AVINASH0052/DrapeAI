# Sugatai (ex-DrapeAI) — Repository Audit

**Date:** 2026-07-29 · **Branch:** `main` @ `65faa95`

> **Status:** P0 and P1 are fixed in the working tree (uncommitted). See
> [Fix log](#fix-log) at the bottom for what changed, what was verified, and the
> three console steps only you can do. P2–P4 are untouched and still open.

**Use case:** India-first AI wardrobe stylist. Photograph clothes → AI tags them → rule engine + LLM generate outfits → try-on visualization on a saved full-body photo. Flutter app + FastAPI/Postgres backend + React admin + new React marketing site.

**Stack found:** `api/` FastAPI (107 py files, 123 tests) · `app/` Flutter (64 dart files, 35 tests) · `admin/` Vite+React · `web/` Vite+React landing (new, Sugatai-branded) · `infra/` Docker Compose/Swarm + nginx · `docs/` 54 md files · `design-system/sugatai/` new brand spec.

Overall: the product is far more built than the roadmap docs suggest. The problems are almost all in **deployment plumbing, cost controls, and an incomplete rebrand** — not in feature code.

## P0 — Will break in production

### 1. Alembic is 5 migrations behind the raw SQL
Alembic head is `0003_try_on_jobs` (≈ SQL migration 0009). Raw SQL migrations `0010`–`0014` have **no Alembic revision**:

| SQL migration | Adds |
|---|---|
| `0010_tryon_input_checks.sql` | `items.tryon_ref_checked_key`, `items.tryon_ref_ok` |
| `0011_try_on_sessions.sql` | `try_on_sessions` table |
| `0012_item_processing_status.sql` | `items.processing_status` |
| `0013_item_display_name.sql` | `items.display_name` |
| `0014_avatar_profile.sql` | `users.avatar_status/_base_key/_profile/_error/_analyzed_at` |

`.github/workflows/deploy.yml` runs **only** `alembic upgrade head`. A production deploy therefore lands code that queries columns the database does not have. `api/app/database/queries/items.py`, `api/app/models/item.py`, `api/app/workers/tasks.py` and the avatar routes all reference them → 500s on wardrobe list, upload, and avatar setup.

**Fix:** write Alembic revisions 0004–0008 mirroring SQL 0010–0014, or switch the deploy step to apply `db/migrations/*.sql` in order. Pick one migration system; running two in parallel is what caused this.

### 2. Flutter's default API URL is a dead ngrok tunnel
`app/lib/core/constants/environment.dart` — on iOS/Android with no `--dart-define`, `apiBaseUrl` returns
`https://ca88-2409-40e3-...ngrok-free.app`. A release build made without `USE_PROD_API=true` or an explicit `API_BASE_URL` ships pointing at nothing. Make prod the default for release builds and keep the tunnel behind a debug flag.

### 3. Domain mismatch across three layers
- App prod target: `https://api.sugatai.com`
- nginx: `server_name api.drapeai.app`, cert path `/etc/letsencrypt/live/api.drapeai.app/`
- API CORS prod allowlist: `["https://drapeai.app"]`

Nothing currently serves `sugatai.com`. Needs DNS + certs + nginx/CORS update before any Sugatai-branded build can talk to the backend.

### 4. Android Firebase config is a placeholder
`app/lib/firebase_options.dart` has `appId: '1:923334398143:android:drapeai_placeholder'`, and only `google-services.json.example` is in the repo. Android auth and FCM will fail. Re-run `flutterfire configure` against the Firebase project you intend to ship with.

## P1 — Security and cost

### 5. No spend cap on the expensive AI providers
`api/app/utils/cost_tracker.py::check_budget` only has caps for `openai` and `anthropic`; everything else falls through to `float("inf")`. Worse, `check_budget` is called from **exactly one place** (`outfit_service.py`, lines 103–104). The paths that actually cost money — Gemini image generation (primary try-on), Cloudflare, NVIDIA, RunPod, vision tagging, embeddings — have no budget guard at all. One abusive account produces an unbounded bill. Add per-provider caps and call `check_budget` in `image_gen_provider`, `vision_tagger`, and `embedder`.

### 6. Live API keys sitting in the repo root
`.env` contains a real `GEMINI_API_KEY` and a real `RUNPOD_API_KEY` (an account-scoped key). It is gitignored and was never committed — verified via `git log --all -- .env` — so nothing leaked, but rotate both and move them into the server's secret store rather than a file next to the source.

### 7. `GoogleService-Info.plist` is tracked despite .gitignore
Both `./GoogleService-Info.plist` and `app/ios/Runner/GoogleService-Info.plist` are in git (the ignore rule was added after they were committed), exposing the iOS Firebase API key and project ID in history. These are semi-public client keys, so severity is low — but `git rm --cached` them and restrict the API key in Google Cloud Console / enable App Check.

### 8. `ENVIRONMENT` misconfiguration is a full auth bypass
`verify_firebase_token` accepts the literal string `test-token` when `environment == "development"`. The gate is correct, but a mis-set env var on the server turns into anonymous admin-capable access. Add a startup assertion that refuses to boot if `ENVIRONMENT != "production"` on the prod host.

README still advertises "CI/CD (test + deploy + Alembic)". Restore a `pytest` + `flutter test` workflow on PR — it would have caught #1.

## Fix log

Applied 2026-07-29. Scope: **P0 + P1 only**. Decisions taken: Alembic is the single
migration source; bundle IDs move to `com.sugatai.sugatai`; the palette conflict
(#15) was deliberately left open.

### P0

**#1 Alembic drift** — added five revisions extending the chain from
`0003_try_on_jobs` to a new head `0008_avatar_profile`:

| New revision | Mirrors |
|---|---|
| `0004_tryon_input_checks` | `0010_tryon_input_checks.sql` |
| `0005_try_on_sessions` | `0011_try_on_sessions.sql` |
| `0006_item_processing_status` | `0012_item_processing_status.sql` |
| `0007_item_display_name` | `0013_item_display_name.sql` |
| `0008_avatar_profile` | `0014_avatar_profile.sql` |

Every revision has a working `downgrade()` and uses `IF NOT EXISTS`, so
`alembic upgrade head` is a safe no-op against a database already built from
`init.sql`. `api/db/migrations/README.md` now declares Alembic canonical, maps
every SQL file to its revision, and documents the stamp-and-recover path.

**#2 Dead ngrok default** — `environment.dart` rewritten. Resolution order is now
`API_BASE_URL` → production (when `USE_PROD_API=true` **or** `!kDebugMode`) →
`DEV_TUNNEL_URL` → localhost. A release build can no longer reach a tunnel or
localhost. The hardcoded ngrok URL is gone; supply one per-run via
`--dart-define=DEV_TUNNEL_URL=…`. `enableDevTestFlow` is additionally gated on
`kDebugMode`, so the test-token entry cannot appear in a release build even if
the define is passed. Added a debug-variant `AndroidManifest.xml` with
`usesCleartextTraffic` so the new `http://10.0.2.2:8000` default works on
Android 9+; release builds keep cleartext disabled.

**#3 Domains** — nginx now serves `api.sugatai.com` with matching cert paths, and
port 80 accepts both hostnames and 301s to the new one (drop `api.drapeai.app`
once nothing points at it). CORS moved out of the hardcoded list into
`CORS_ORIGINS`, defaulting to `https://sugatai.com,https://www.sugatai.com`.

**#4 Bundle IDs** — `com.drapeai.drapeai` → `com.sugatai.sugatai` across iOS
pbxproj, Android `namespace`/`applicationId`, the Kotlin package directory
(`MainActivity.kt` moved via `git mv`), macOS xcconfig and pbxproj, and
`google-services.json.example`. Dart package renamed `drapeai` → `sugatai` in
`pubspec.yaml` with all `package:drapeai/` imports updated. macOS build product
renamed `drapeai.app` → `sugatai.app` including `TEST_HOST`. `firebase_options.dart`
now throws an actionable `StateError` on Android instead of failing obscurely on
the placeholder app ID.

### P1

**#5 Spend caps** — added caps for gemini/cloudflare/runpod/nvidia/groq plus a
`TOTAL_SPEND_CAP_USD` backstop. Unknown providers now fall back to the total
ceiling rather than `float("inf")`. New non-raising `within_budget()` is wired
into **both** cascades: `ai_provider.call_role` (covers vision tagging,
embeddings, ranking, chat) and `image_gen_provider` (both try-on paths). An
over-budget provider is skipped like an unconfigured one and the next is tried;
when all are exhausted, try-on falls through to the local composite instead of
billing. A failure inside the budget check logs at ERROR and allows the call, so
a tracking outage degrades rather than takes down try-on.

**#7 Firebase plists untracked** — `git rm --cached` on both copies (files remain
on disk, builds unaffected). Added `ios/Runner/GoogleService-Info.plist.example`
to match the existing Android template.

**#8 Environment guard** — `_validate_environment()` runs at import. Rejects any
`ENVIRONMENT` outside `{development, staging, production}`; rejects
`REQUIRE_PRODUCTION=1` paired with a non-production environment; in production
requires `FIREBASE_PROJECT_ID` and refuses a `*` CORS entry. `REQUIRE_PRODUCTION: "1"`
set on api and worker in both prod and swarm compose files.

Also filled the `.env.example` gaps noted in #20 (`ANTHROPIC_API_KEY`,
`GROQ_API_KEY`, all spend caps, `CORS_ORIGINS`, `REQUIRE_PRODUCTION`, model overrides).

### Verified

- Each revision's columns, tables, indexes, constraint names and CHECK value

- Budget logic exercised directly: every routed provider has a finite cap;
  unknown provider falls back to the total cap; skips at the provider cap; skips
